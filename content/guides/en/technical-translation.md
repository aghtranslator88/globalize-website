# Technical Translation Services

**Short answer:** Globalize lists technical translation among its services. To request an assessment, describe the material, subject, source and target languages, file format, and intended use. The specific scope and language availability must be reviewed for each request; translation does not certify technical correctness or regulatory compliance.

## Prepare a technical translation enquiry

Technical material can use specialized terms, abbreviations, diagrams, tables, warnings, and product-specific naming. Give enough context to identify what the content describes and who will use the translated material. If your organization has approved terminology or reference documentation, include it with the enquiry.

Useful details include:

- Content or document type and approximate volume
- Subject area and intended user or recipient
- Source and target languages
- Available file formats and whether the content is editable
- Any glossary, style guide, prior translation, or terminology instruction
- Requested timing and any layout or technical constraints

These are scoping questions, not a promise that every technical discipline, format, or layout task is supported.

## Translation is not technical certification

Translation transfers the source content into another language. It does not test a product, validate calculations or specifications, certify safety, approve regulatory compliance, or replace engineering or subject-matter review. The responsible technical professional or recipient determines whether the content meets its requirements.

## Preserve labels, units, and warnings

Technical meaning often depends on more than the sentence. Keep a consistent relationship between a label and the part, measurement, warning, or procedure it describes. Provide the controlling product version and any approved glossary so repeated component names and commands can be checked consistently. Mark content that is locked, repeated by design, or legally required to remain unchanged.

| Source feature | Instruction to include |
|---|---|
| Product/version | Model, release, and intended user |
| Measurements | Units, tolerances, decimal notation, and whether values must remain unchanged |
| Diagrams/tables | File source, labels, callouts, and references in the text |
| Warnings | Required wording, hierarchy, and linked precaution text |
| Terminology | Approved component names, abbreviations, and reference version |
| File constraints | Editable text, layout limits, and dependencies on engineering files |

Review the translated labels and instructions against the same product version that will be used. A translation does not independently verify a measurement, test a device, approve a safety instruction, or establish compliance. Route technical questions to the responsible engineer or product owner. If text changes after translation or the product version changes, identify affected strings and ask whether a new review is needed.

## Supply the technical context and reference set

A technical file is easier to translate when the source is accompanied by product or process context. Identify the equipment, software, component, procedure, or audience involved, and provide diagrams, interface captures, earlier manuals, approved terminology, and the relevant version number where available. Explain whether the text is for operators, technicians, engineers, customers, or regulators; the same term may require different wording depending on its function.

Keep warnings, prerequisites, numbered steps, labels, and cross-references visible. If an instruction points to a diagram, part number, menu item, or safety label, include that item or identify it precisely. A translator can preserve the stated instruction but cannot test a machine, validate a software build, certify compliance, or decide that an unsafe instruction is acceptable.

| Technical element | What to identify before work |
|---|---|
| Terminology | Preferred term, prohibited alternatives, and definition in context |
| Measurements | Units, tolerances, symbols, and any supplied conversion rule |
| Procedures | Sequence, prerequisite, warning, and expected result |
| Interface text | Screen, button, menu, variable, or string identifier |
| Revisions | Source version, change list, and files that supersede earlier copies |

## Preserve the relationship between text and operation

For manuals and procedures, a sentence can be grammatically correct yet operationally unclear if a condition, warning, or step order is misplaced. Review headings, step numbers, callouts, labels, and references as a connected system. If repeated terms are intentionally different for separate components, document that distinction instead of normalizing them all to one word.

Send editable source files when the target requires text to be returned in a specific file type. If only a PDF or image is available, note whether the requested output is translation, recreated layout, or both. These are separate scope questions. Identify text embedded in drawings, screenshots, diagrams, and code comments so it is not overlooked. Do not assume that every file format or desktop-publishing task is available without a project-specific assessment.

During review, check model numbers, part numbers, warnings, negative instructions, decimal marks, units, and references against the original. Do not silently “correct” a value that looks unusual. Flag it for the technical owner. The owner should verify that the translated instruction matches the approved source and current product revision before use. Translation alone is not a substitute for engineering, safety, regulatory, or usability validation.

## Control revisions and questions during production

Assign one owner to answer terminology or source questions and provide a dated source version. If a product label, screen, or procedure changes during the assignment, identify the changed passages and send the updated reference files together. Keep approved wording for warnings and recurring interface labels in a controlled glossary. A change log helps the reviewer confirm that the translated manual corresponds to the current source rather than an earlier revision. Do not merge feedback from multiple reviewers until the technical owner resolves contradictory instructions.
